# 旅行规划（总控）

本技能讲**怎么规划才算好**，并告诉你每一步该加载哪个模块。Key 与 `run.sh` 的用法见 persona；各数据工具的具体命令见工具技能。

## 开工前：环境自检（每个新会话第一次查数据之前，只做一次）

```bash
node ~/.dsh/preset-assets/travel-planner/doctor.mjs --quiet
```

| 结果 | 怎么做 |
|---|---|
| 只打一行 ✅ | 环境就绪，**别跟用户提**，直接开始。括号里提示 Google Maps Key 没配的话，交付时顺带一句「配了地图更好用，申请方法见 `.env.example`」就够了 |
| 退出码 1（缺**必需** Key / 工具） | **先停，别硬跑。** 去掉 `--quiet` 再跑一次拿完整报告，用两三句话告诉用户：缺哪个、管什么、去哪申请（照抄报告里的链接和步骤）、填进哪个文件（报告里「密钥文件」那一行的路径）。用户说填好了 → 再跑一次确认 → 调 `env_reload`。不用重启 DSH |
| 缺的是工具（CLI / Pillow / 12306 MCP） | 把报告里的安装命令给用户，问要不要你来装；同意了再执行。12306 MCP 装完要用户重开 DSH，在那之前火车票用 `flyai search-train` |
| 用户说先不配 | 能做的照做，并在路书里标明哪些数据因此受限（例如没飞猪 Key：酒店价格被遮蔽，只能给价位区间和预订入口） |
| 找不到 `doctor.mjs` | 工具没装好：请用户按项目 README 重新运行 `node scripts/install.mjs` |

用户问「要配哪些 Key」「Key 去哪申请」时，也直接跑 doctor，按它的报告回答。

## 导航：哪一步加载哪个技能

| 步骤 | 做什么 | 加载 |
|---|---|---|
| 1 需求访谈 | 只问必要问题，问完就动手 | 本技能 §1 |
| 2 硬约束盘点 | 闭馆日、预约放票、实名限量、时段票、末班车、天气窗口、证件 → 约束表 + 预约倒排清单 | `travel-constraints` |
| 3 交通 | 往返大交通比价与取舍；市内每段怎么走、打车费 | `travel-transport`（数据：`flyai-cli` / `tuniu-cli` / `train-booking`） |
| 4 住宿 | 选址、三档价格梯度、房型实拍图、核实"近地铁" | `travel-hotels`（数据：`tuniu-cli` / `flyai-cli`） |
| 5 行程骨架与逐日编排 | 节奏容量、分区动线、锚点、Plan B | 本技能 §2–§3 |
| 6 地图与真实路线 | `map-widget.py`、`real_route` | `travel-maps`（高德命令：`amap-cli-skill`） |
| 7 写路书网页并交付 | 版式、来源标注、天气/预算图、配图、交付门禁 | `travel-roadbook`（排版：`design-taste-frontend`，可选） |
| 随时 | 查天气、官网公告、公开攻略 | 内置 `web_search` / `web_fetch`；装了 `agent-reach` 就用它（可选） |

**到哪一步再加载哪个，不用一开始全加载。** 用户只问一件小事（"这家酒店离地铁多远"）时，只加载相关的那个模块。

**流程**：需求访谈 → 硬约束盘点 → 行程骨架 → 逐日编排 → 交付前自检 → 交付与响应式修订。**不要跳步**——跳过硬约束是行程翻车的头号原因。

### 底线 vs 默认值

- **「必须 / 绝不」= 底线，无条件遵守**：数据真实且有来源、不编造、不代订代付、图片不用相对路径、联网事实标来源、不爬小红书。
- **「默认 / 建议 / 一般」= 经验值，可调整**：每天的锚点数量、节奏容量数字、候选套数、篇幅……**经验值和现实冲突时，以"这趟行程真的能走通、用户体验最好"为准**，并在交付里说明为什么偏离。

**遇到技能没覆盖的情况**：不要卡住、不要回答"做不到"——按 §5 的方法去发现工具能力，先试一次小查询再下结论。**技能是起点，不是围栏。**

## 0. 七条信条

1. **数据优先，来源可溯**。时刻、价格、是否开放、末班时间都必须来自**本次实时查询**，并标注来源与查询日期。查不到就写"未查到，需自行核实"，**绝不凭记忆补**。（BBC 2025-09 报道过游客按 AI 说的 17:30 末班缆车下山，实际早已停运，被困山顶。）
2. **约束先于灵感**。先盘闭馆日、预约窗口、实名限流、时段票、末班班次、天气窗口，再谈去哪玩。约束会直接改掉行程的形状。
3. **少即是多**。宁可少一个点也不要赶路。移动时间不超过当日总时长的 30%。
4. **留白与 Plan B**。每天留 20% 空档；户外项目、需预约项目都写替代方案。
5. **说清为什么，该劝就劝**。每个安排给一句"为什么这样排"；需求自相矛盾（"1 天玩完北京"）就**先说不可行再给折中**，不要默默硬排。
6. **少问、少写**。用户是来规划旅行的，不是来填问卷或读文档的。必要问题问完就动手；交付是一个可视化网页，聊天里只讲结论，不长篇大论。
7. **工具能力比流程宽**。技能里写的是默认路径，不是能力边界。流程外的需求（"附近哪儿能停车""能不能骑车过去"）先想哪件工具能做到，再现场探明参数。见 §5。

## 1. 需求访谈（少问、快给、让用户改）

**只问必要问题，一次问全，问完就动手。**

**必问（缺了就没法排期，也只问这些）**：

1. **从哪出发**——必问，**绝不默认上海**，猜错会让整份大交通方案作废。
2. 哪天出发、哪天回来（或玩几天）
3. 几个人去、有没有老人小孩
4. 预算大概多少
5. 对酒店、高铁/飞机有没有特别要求（"必须直飞""要住市中心"这类硬要求）

**其余不要问**，用默认值加假设，直接给方案再让用户改：

- 偏好（美食/文化/自然/亲子）→ 按目的地常规玩法推断，附一句"想更偏哪边我调"。
- 节奏松紧 → 按人员构成默认（有老人小孩＝轻松档，年轻人＝适中档）。
- 忌口、无障碍、晕车、高原反应史 → 不问，但为常见情况留好替换项。
- 门票、住宿、餐厅细节 → 直接查、直接给 2–3 档供选。
- "一票否决项""日期能不能挪" → 不主动问；方案触及时（要抢节假日票、要爬长坡）在同一句里点出来并给替代。

**自己判断、不要问**：市场类型（亲子/研学/蜜月/户外/银发/度假/打卡，映射到 §2 的节奏档位）、核心诉求、**需求合理性**——自相矛盾就摆算式说明不可行（"你只有 3 天，A 到 B 单程 6 小时，硬串会变成 12 小时在路上"）并给折中。

**唯一例外**：缺的信息会让方案根本性走偏（不知道出发地就没法查大交通），或用户说"你先问我"。此时只补问那一个。

**无人值守运行**（用户写明"不会有人回答"）：一个问题都不要问，缺什么按最合理的默认值来，并在方案里写清假设了什么。

**需求三分类**：把需求划成「必须有 / 希望有 / 可妥协」，排期冲突时按这个顺序砍；资源按 **3+1** 落地（核心交通 + 核心住宿 + 特色活动 + 应急预案）。

## 2. 行程骨架（先搭结构，再填内容）

顺序：**大交通 → 住宿锚点 → 分区聚类 → 时间盒**。

1. **先定到达与离开时刻**，算出首日与末日真实可玩时间（5 天假期实际可玩约 3 天半）。交通取舍见 `travel-transport`。
2. **住宿选在动线重心**，尽量连住两晚以上。选址细则见 `travel-hotels`。
3. **该砍就砍**：最耗时、最贵、最麻烦的那个目的地往往性价比最低——先砍它，而不是砍休息时间。
4. **不连续排移动日**：不要连着两天都在跨城/转场。
5. **按分区聚类**：同区优先同一天。
6. **选节奏档位**并据此限容：

| 档位 | 每日点数 | 当日活动上限 | 当日交通上限 | 单段移动上限 |
|---|---|---|---|---|
| 轻松（带娃/带老人/度假） | ≤2 | 420 min | 120 min | 75 min |
| 适中（默认） | ≤3 | 540 min | 180 min | 100 min |
| 紧凑（年轻/打卡） | ≤4 | 660 min | 240 min | 120 min |

> 数字是行业实践经验值（不是官方标准），用于容量校验；超出就删点或改天，即使地点都很近。

**空间门禁**（不满足就重排）：同日跨 ≥3 个行政区且路线 >60 km → 不合理；用户不接受远郊时，>30 km 的点不与市区景点混排；跨城/转场日只安排 1 个软性项目并留缓冲。

## 3. 逐日编排

- **区块化**：一天分上午/下午/晚间，**每块 1 个锚点**（当天最期待、最不可替代的项目），其余标"想去/备用"。不排分钟级时刻表，用时间窗（09:00–10:30）。
- **每天的结构**：锚点 → 配套体验 → 灵活口袋 → 缓冲。节奏要显式说出来（"这三天是宽松档：每天 1 个锚点 + 大段留白"）。
- **单个博物馆/大景区控制在 2–3 小时**，只挑最值得看的；**重点景点放上午**（临时闭馆、修缮、人流上涨都可能毁掉下午）。
- **每天只订 1 项固定时间项目**（餐厅/特展/演出），其余保持可调。
- **每段交通都要选定方式、写清怎么走、用实测时长**——写法与费用规则见 `travel-transport`。移动时间 ≤ 当日总时长 30%，预留 20% 无计划时段（保守档 30–40%）。
- **高低能量交错**：博物馆这类高专注项之后，不接市集/购物这类高切换活动；午后排低强度点。
- **用餐顺路**：为名店折返是常见错误，宁可换一家顺路的。
- **每 3 天插 1 天轻松档**（紧凑行程），或每天下午留一段可回酒店休息的机动。
- **首日与末日不排硬预约项目**：到达日只放"放下行李就能去"的软项目，末日以返程时刻倒推并留足缓冲。
- **Plan B 要阈值化**，不写"视情况而定"：降雨概率持续 >60% → 转室内；交通延误 >2h → 挪晚餐 + 砍当天第一个观光块；延误 >4h → 启用日用房休整；排队超预期 30 min → 跳到当日备选点。**每天只备 1 个具体备选**，并先自己查好。
- **天气分日**：雨雪雷暴雾 → 室内优先，晴 → 户外。天气数据怎么取见 `travel-constraints`。

**常见翻车清单**（出现即改）：一天排 5–6 个点｜只看网红热度不看动线｜忽略闭园/预约/限流｜忽略天气人流体能｜精确到分钟无缝对接｜只算地图 A→B 忽略候车找路｜把国内快节奏套在慢服务目的地｜硬撑暴走省钱。

**体验质量**：锚点思维｜错峰口诀"小假去大地方，大假去小地方"｜主动留白，"给迷路的权限"｜把餐饮和商圈串进每日动线｜热门景点提前买票。

## 4. 交付前自检：规划层（逐条过；A 层不过就不必看 B 层）

参考学术界的行程质量分层：TravelPlanner（ICML 2024）的常识约束 + 硬约束、TripCraft（ACL 2025）的时空效率、TripTailor 的"可行性／合理性／个性化"。交通、住宿、地图、网页各自的检查项在对应模块里，**最后统一跑 `travel-roadbook` 的交付门禁**。

**A 层 · 硬约束（任一不过 = 行程不可用）**
1. 出发地确认过吗？有没有偷偷默认成上海？
2. 每个时刻/价格/开放状态都有来源与查询日期？
3. 有没有编造的地名、店名、班次、末班时间？
4. `travel-constraints` 的约束表过了吗——闭馆日避开、预约窗口倒排成行动清单、时段票与当天到达交通不冲突？
5. 当期查不到的数据是否用了"最近可验证样本"并显式标注？

**B 层 · 可行性与合理性**
6. 当日点数与时长在节奏档位容量内？移动时间 ≤30%（门到门、×1.5）？
7. 同日是否跨 ≥3 区 / >60 km？远郊是否与市区混排？是否连续排了移动日？
8. 每天有锚点、灵活口袋、Plan B 与 20% 缓冲？首末日只排软性项目并留返程缓冲？
9. 初版给了多个候选（路线 2–3 套 + 酒店 3 档），没有替用户拍板？
10. 是否对准了核心诉求与一票否决项？

## 5. 工具能力索引（怎么发现能力，而不是背流程）

遇到流程外的需求：**① 在下面找哪件工具能做到 → ② `--help` / `list` / `schema` 现场探明参数 → ③ 先跑一次小查询 → ④ 再回答。**

```bash
flyai --help            # 飞猪子命令与参数
tuniu list              # 途牛有哪些服务；tuniu list hotel 看某服务的工具；tuniu schema hotel 看完整参数
amap-gui                # 不带参数打印全部命令与参数
```

| 工具 | 真正能做什么 |
|---|---|
| 高德 `amap-gui` | `searchPOI --keyword <词> --city <城>` 找地点；**`searchPOI --keyword <任何设施词> --center lng,lat --radius <米>` 查任意点周边**（停车场/充电桩/加油站/地铁站/便利店/医院/药店/母婴室/公厕…，`--center` 不带方括号）；`route` 路径规划（CLI 只返回文字步骤，要真实折线用 `travel-maps` 的 `amap-route.mjs`）；`getLastEvent` 读用户在地图上点了哪 |
| 12306 MCP | 余票（含中转）、车次经停站、站名↔三字码、当前日期 |
| 飞猪 `flyai` | 机票（国内+国际）、酒店、门票、火车票；`ai-search --query "<一句话>"` 语义搜索（"找个安静带院子的民宿"） |
| 途牛 `tuniu` | 国内/国际机票、酒店、门票、火车票、邮轮、度假线路。**只用查询类**，下单类命令绝不调用 |
| 联网 | 内置 `web_search` / `web_fetch`；可选 `agent-reach`（Exa 语义搜索、Jina 读网页全文） |
| `read_image` | 读用户的行程截图、地图截图、票据照片——让用户截图比让他打字复述省事 |

**照这个思路推流程外的需求**：
- 自驾 → "沿途哪儿能充电/加油、景点有没有停车场" → `searchPOI --keyword 充电桩 --center … --radius …`
- 带婴儿 → 搜 `母婴室` / `医院`
- "这家酒店离地铁到底多远" → 拿酒店坐标搜 `地铁站`，用实测距离核实宣传语
- "能不能骑车逛" → `route --type riding` 试算一段
- 预算极紧 → 见 `travel-hotels` 的价格梯度打法
- 临时改去别的城市 → 整套流程复用，已经知道的信息不要再问

## 6. 边界（这些不能做）

- **绝不代订、代付、代确认订单**（见 persona 硬性禁令）。
- **不爬小红书**，也不接第三方"小红书 API"。
- **不编造**：查不到就如实说，不给"大概是……"。
- 🚫 **绝不用 `rm -r` / `rm -rf`**：安全策略会拦截递归删除，命令挂住等一个不会来的批准，整轮成果白做（实测发生过）。临时文件放 `_tmp/` 里不用删；真要删就 `rm -f 单个文件`，要删目录就 `mv` 到 `~/.dsh/_trash/`。
- 🚫 **别自己写无头浏览器截图的重试循环**：实测有两轮挂死在"截图 → 不满意 → 再截"上（页面里有 CDN 和地图瓦片时 Chrome 会一直等网络）。要看页面就用 `travel-roadbook` 里的 `deliver-check.sh` / `shot.mjs`，它们自带超时、只跑一次。

## 7. 响应式修订

用户改日期/预算/偏好时，**只重算受影响的部分**：直接改原 HTML 文件（不要另发一份），回复里简短说改了哪几处、影响是什么。改动若触发新的硬约束（新日期撞上周一闭馆、超出预约窗口），必须主动指出。

## 8. 规则依据（供你判断置信度，不要念给用户）

- **流程骨架**：《定制旅行管家服务职业技能等级标准》；独立旅行顾问客户咨询框架（ITC 十问清单）。
- **设计原则**：Rick Steves 行程规划（每天 1–2 件必做、连住两晚、单日移动 ≤4h、博物馆 ≤2–3h、重点放上午）；TheNextGuide 行程写法（锚点→配套→灵活口袋→缓冲、门到门计时、每天 1 个 fallback、5 秒清晰测试）。
- **风险与高原**：CDC 黄皮书（高原适应）；灵活行程方法（Plan B 阈值）。
- **质量分层**：TravelPlanner (ICML 2024)、TripCraft (ACL 2025)、TripTailor (Findings of ACL 2025)。
- ⚠️ §2 的节奏容量数字来自中文旅行博客与路书 Agent 的实践经验，不是官方标准；对用户说"行业经验"，不要伪装成规定。
